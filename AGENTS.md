# AGENTS.md — Coding Rules

Rules for anyone (human or agent) writing code in this repository. They describe **how** to build; the
**what** lives in the spec and is not negotiable here.

**Source of truth for behaviour:**
- `_bmad-output/specs/spec-hotkey-grammar-corrector/SPEC.md` — capabilities, constraints, non-goals
- `.../llm-provider-contract.md` — the 5 provider principles, default provider, `suggestions[]` shape
- `.../risks.md` — Wayland hotkeys, X11 primary selection, resident RAM
- `PLAN.md` — roadmap and decisions already made (do not re-litigate them)

If a rule below appears to conflict with the SPEC, the SPEC wins — and say so in your output instead of
silently choosing. Never hand-edit `SPEC.md`; it is regenerated by `/bmad-spec`.

**Target:** Flutter desktop, **Linux first** (X11 *and* Wayland). Resident tray daemon. No Electron, no
webview. A mobile path stays open but is out of scope — don't build for it, don't foreclose it.

---

## 1. Readable by humans first

Code is read far more often than it is written, and this project will be read by contributors who did not
attend the design conversation.

- Optimise for the next reader, not for line count, not for cleverness. If a shorter form is harder to
  follow, use the longer one.
- Names carry the meaning: `CorrectionProvider`, `panelVisibility`, `activePreset`. No `mgr`, `tmp`,
  `data2`, `doStuff`. A name that needs a comment to be understood is the wrong name.
- Comments explain **why**, never **what**. `// Wayland gives no key grabs, so this routes through the
  portal` is useful. `// increment counter` is noise — delete it.
- Nesting is a smell. Prefer early returns and guard clauses over `if` pyramids. Three levels of
  indentation inside a function is a signal to extract.
- No dead code, no commented-out code, no `TODO` without a concrete follow-up note. Delete it; git
  remembers.
- Consistency beats personal taste: match the surrounding code even if you'd have written it differently.

## 2. Small functions, one job each

- A function does **one** thing at **one** level of abstraction. If you need "and" to describe it, split it.
- Keep functions short enough to read without scrolling (roughly ≤ 20 lines is the norm; long `switch`
  expressions and widget trees are the honest exceptions).
- Never mix decision-making with I/O in the same function. Decide in a pure function, act in a thin one.
  Pure logic is what tests can reach.
- No boolean flag parameters that select between two behaviours (`correct(text, retry: true)`) — write two
  named functions.
- Parameter lists stay short. Past ~3 arguments, pass a named record or a small value class.
- A function either returns a value or causes an effect, not both, wherever that's practical.

## 3. Single responsibility per class

- One class, one reason to change. The clipboard reader does not know about the LLM. The hotkey layer does
  not know about widgets. The panel does not know which provider is active.
- One public type per file; file name is the snake_case of the type (`correction_provider.dart`).
- Widgets are for presentation. No network calls, no database writes, no clipboard access, no prompt
  building inside a `build()` method or a widget class.
- Persistence stays behind a repository-style type. UI and domain code never touch SQL, and never see a
  database row type.
- Configuration is loaded and validated in exactly one place, then handed around as an immutable value.
  Nothing else reads the config file.

## 4. Program to abstractions

Depend on interfaces you own; let concrete implementations sit at the edges and be injected inward.
Dependencies point from the outside in — UI → domain → interfaces; never domain → Flutter, never domain →
a vendor SDK.

### 4.1 The LLM provider interface is load-bearing

This is the abstraction the whole product bets on. Everything in `llm-provider-contract.md` is binding:

1. **Text in, stream out.** The interface takes text and returns a stream. It is **not** HTTP-shaped. A
   provider may be a local process, an SDK call, or a network API — none of that appears in the signature.
   No `Uri`, no headers, no status codes, no `http.Response`, no retry/backoff policy, no API key in the
   interface or in any caller.
2. **Many described, one active.** Config may describe many providers; exactly one is active per
   correction. Selection happens in config or in-app settings — never in code, never at runtime by
   negotiation. **No cascade, no fallback, no racing backends.** If you find yourself writing
   `try providerA … catch → providerB`, stop: that pattern is ruled out by the SPEC.
3. **Preset = prompt + model, together.** They travel as one unit so that "try a faster model" is a config
   edit, not an engineering task. Never accept a model id without its prompt, or vice versa.
4. **Stateless sessions.** Every correction is a fresh session. A provider implementation that caches,
   accumulates conversation state, or feeds history back into a prompt violates the contract.
5. **Structured response.** A provider returns a structured `suggestions[]` — a list of register variants
   of the same correction — never a prose blob the caller has to parse. **The same shape is what the
   history database stores** (CAP-7); provider design *is* analytics design. Do not let a "wire model" and
   a "db model" drift into two shapes.

Illustrative sketch — **the architecture step fixes the final names and fields**, but any final design must
keep these properties:

```dart
/// One register variant of a correction. Same shape the history DB persists.
final class Suggestion {
  const Suggestion({required this.label, required this.text});
  final String label; // formal | casual | shorter
  final String text;
}

/// Prompt and model, bound as one unit. Never separated.
final class Preset { /* ... */ }

sealed class CorrectionEvent {}
final class SuggestionDelta   extends CorrectionEvent { /* partial text, streamed */ }
final class CorrectionFinished extends CorrectionEvent { /* List<Suggestion> */ }
final class CorrectionFailed  extends CorrectionEvent { /* message the panel can render */ }

abstract interface class CorrectionProvider {
  /// Text in, stream out. Stateless: no state survives between calls.
  Stream<CorrectionEvent> correct({required String text, required Preset preset});
}
```

- Provider **failure is part of the return type**, not an exception that escapes to the framework — CAP-13
  needs it rendered inline in the panel with a working Retry.
- The stream must be **cancellable**. A hidden panel or a Retry must be able to abandon an in-flight
  correction and leave nothing running.
- Every provider gets a fake/stub implementation used by tests. If the interface is awkward to fake, the
  interface is wrong.

### 4.2 The other abstractions worth owning

Same discipline, smaller stakes: put an interface in front of anything platform- or vendor-specific so it
can be faked in tests and swapped without touching call sites.

- **Global hotkey** — X11 grabs and the Wayland XDG GlobalShortcuts portal are *implementations* behind one
  interface. Read `risks.md` first: Wayland grants no free key grabs and behaviour varies by compositor.
  Nothing above this interface may assume X11 semantics.
- **Clipboard** — read and write behind an interface. Nothing above it may assume X11 primary selection
  exists; that is phase-2 and X11-only.
- **Window/panel visibility, tray, history store, config, clock** — same treatment.
- Don't invent an abstraction for a single implementation with no platform variance, no test need, and no
  spec requirement. Abstractions are justified by variation that actually exists.

## 5. SOLID, applied here

- **S — Single responsibility.** See §3. The unit of blame for a change should be one file.
- **O — Open/closed.** Adding a provider, a preset, or a display-server backend means adding a file and a
  config entry — not editing a `switch` in the correction pipeline. If a new provider forces a change in
  domain code, the seam is in the wrong place.
- **L — Liskov.** Every implementation must honour the whole contract: streams partials, terminates,
  reports failure as an event, stays stateless, respects cancellation. A provider that throws instead of
  emitting a failure event, or that only ever emits one final chunk, is a broken substitute — not a
  variant.
- **I — Interface segregation.** Narrow interfaces. `CorrectionProvider` corrects text; it does not
  validate config, count tokens, or persist history. Never make callers depend on methods they don't use.
- **D — Dependency inversion.** Domain and UI depend on interfaces defined in the domain; concrete
  providers, portals, and databases depend inward. **No singletons and no service locators reached from
  inside domain code** — pass dependencies in through constructors, wire them once at the app's
  composition root.

## 6. Flutter and Dart practice

Current (Dart 3 / modern Flutter) style. The linter is the floor, not the ceiling.

- `analysis_options.yaml` from day one: `flutter_lints` plus stricter language settings
  (`strict-casts`, `strict-raw-types`). **A clean `dart analyze` is a merge requirement** — no ignore
  comments without a one-line justification.
- `dart format` output only. No hand-formatting arguments.
- **Immutability by default:** `final` fields, `const` constructors wherever possible, `const` widgets in
  trees. Immutable state objects with `copyWith`; never mutate shared state in place.
- Use the modern language properly: **sealed class hierarchies + exhaustive `switch` expressions** for
  states and events, records for small tuples of returns, pattern matching over `is`-chains and
  null-checks. Exhaustive switches are how the compiler protects you when a case is added.
- **Sound null safety, honestly.** No `!` to silence the analyzer, no `late` as a workaround for unclear
  lifecycles, no `dynamic`. If a value can be absent, model the absence.
- **Widget rules:** `build()` is pure and cheap — no I/O, no `async`, no allocation of controllers or
  subscriptions. Prefer `StatelessWidget`; reach for state only when the widget genuinely owns it. Extract
  widgets into named classes rather than `_buildFoo()` helper methods (better rebuild scoping, better
  reads). Every `Stream`/`Timer`/controller created is disposed in `dispose()`.
- **State management:** one approach, chosen at the architecture step, used consistently. Never two
  competing patterns in one codebase, and never business logic living in a widget's `setState`.
- **Async:** always `await` or explicitly and visibly discard futures; propagate `CancellationToken`-style
  cancellation for streaming corrections; never `Future.delayed` to paper over a race.
- **Errors:** expected failures (provider error, bad config, no clipboard content) are modelled values that
  the UI can render. Exceptions are for programmer error. Never `catch` broadly and swallow; never let an
  exception cross an abstraction boundary as a vendor type.
- **Performance, because CAP-1 is 100 ms:** the hotkey path only toggles visibility of an already-built,
  already-warm window — it constructs nothing, loads nothing, and awaits no I/O. Keep expensive work off
  the show path and off the UI isolate. The daemon is resident all day: watch allocations, dispose
  everything, measure the footprint rather than trusting the ~96 MB baseline (`risks.md`).
- **Platform code:** any `Platform.isLinux` / display-server branch lives in one implementation file behind
  an interface (§4.2) — never sprinkled through the app.

## 7. Tests

- Domain logic and prompt/response mapping are pure Dart and unit-tested without a Flutter binding.
- Providers, clipboard, hotkeys, storage, and config are tested through fakes of their own interfaces.
- Every capability that says "success:" in the SPEC deserves a test that would fail if the behaviour
  regressed. Cite the CAP id in the test name.
- Test names read as behaviour, not as method names: `panel stays open after copying a suggestion`.
- Don't test the framework, don't assert on private internals, don't chase coverage numbers.

## 8. Never do this

- Add fallback, cascade, or "instant local draft replaced by the remote answer" behaviour. Explicitly ruled
  out by the SPEC.
- Fake perceived speed — placeholder text, canned suggestions, staged spinners. Speed must come from
  residency and real streaming.
- Let HTTP, an SDK type, an API key, or a model id leak past the provider interface.
- Build a settings screen that only mutates memory. Settings and the config file are two synced surfaces
  (CAP-8, CAP-12); a change in one writes through to the other.
- Store history remotely, or store it in a shape different from the provider's `suggestions[]`.
- Construct the panel window on hotkey press.
- Implement a non-goal (diff view, primary selection, invisible replace, personalization, analytics UI)
  because it "was easy while I was in there".
- Rewrite the spec to match the code.

## 9. When something is genuinely unclear

Do the parts that don't depend on the answer, state the assumption you're proceeding under, and flag it in
your output. Don't silently pick a direction on a load-bearing decision — provider contract, hotkey
strategy, history schema, state management — and don't invent a capability the SPEC doesn't list.
