## Intent

**Problem:** `WindowManagerPanelVisibility` mishandles window events three ways, all in one file. (1) `_reconcile`'s `_outstanding > 0` guard discards **every** event while a request of ours is in flight, but the adapter's only platform calls are `show`, `hide` and `focus`, so a `minimize` — emitted from a GTK `window-state-event` — can never be an echo of ours and is nonetheless dropped, leaving an iconified panel that `isVisible` reports as up (DW-31). (2) `_onBlur` returns whenever `_outstanding > 0` on the reasoning that a panel still being mapped cannot have been dismissed; that is false of a `show()` on an **already-visible** panel — what AD-14's second launch and AD-12's tray entry both issue — so a genuine dismissal during that round trip is discarded and nothing re-evaluates it (DW-32). (3) `_onWindowEvent` has no `focus` case at all while handling `blur` destructively, so the adapter never knows whether the window ever held the keyboard; on a window manager with focus-stealing prevention the panel takes itself down at the moment it is summoned (DW-33).

**Approach:** Split echo-capable events from structurally external ones, and make a blur depend on a focus that actually happened. `_reconcile`'s guard is taken **only** for `show`, `hide` and `restore`; `minimize` moves the mirror unconditionally, and a `restore` that undoes a `minimize` this adapter believed is believed in turn, so the pair stays symmetric during one of our requests exactly as it is outside one. Every other `restore` stays behind the guard. The adapter tracks whether the window holds the keyboard from the `focus` and `blur` events, and `_onBlur` does nothing unless it does. A blur that is genuine but arrives while a request is outstanding is **latched** rather than dropped, and reconsidered when `_outstanding` returns to zero — re-checking then that the panel is still up and has not taken focus back.

## Boundaries & Constraints

**Always:**
- The `_outstanding` guard stays exactly as it is for `show` and `hide`, and for every `restore` except the one that undoes a `minimize` this adapter itself believed (next bullet). `restore` is load-bearing: `windowManager.show()` restores a minimised window as part of its own implementation, so a `restore` echo can arrive during one of our requests, and believing it while a hide is queued behind that show strands the hide.
- **The `minimize`/`restore` pair is symmetric — during one of our requests exactly as with nothing outstanding.** A believed `minimize` arms a one-shot latch; the next `restore` consumes that latch and moves the mirror back whatever `_outstanding` reads. A `restore` arriving with the latch clear takes the guard, unchanged. Our own `show()` and `hide()` clear the latch where the intent is *expressed*, not where the mirror moves — after one of our requests a `restore` may be that request's own echo, which is the case the guard exists for, and `windowManager.show()` deiconifying a minimised window is exactly how that echo is produced. The latch is one-shot and is re-armed by nothing but a fresh believed `minimize`. Without it, an unconditional `minimize` and a guarded `restore` leave the mirror reading false over a mapped window with nothing able ever to correct it: `main.dart` sets `setSkipTaskbar(true)`, so the hotkey is the only route to that panel and the press reads as a summon — a fresh AD-18 session discarding what the user had typed into a panel that never left the screen. This is the escalation of 2026-08-15, resolved 2026-08-19; see the Spec Change Log.
- A deferred blur is reconsidered **only** when `_outstanding` reaches zero, and it re-checks state at that moment rather than acting on what was true when the blur arrived: the panel must still be visible, the adapter must not be disposed, and the window must not have taken focus back in between.
- At most one deferred blur is outstanding — a latch, not a queue. Repeated blurs during one round trip are one dismissal.
- The focus-loss log line must still read `the window rejected the focus-loss hide`; `window_manager_panel_visibility_test.dart` asserts `contains('focus-loss hide')` and the two `_dismiss` causes must stay distinguishable.
- AD-1 confinement holds: `package:window_manager` stays in `lib/main.dart` and `window_manager_panel_window.dart`. This change touches neither.
- Logs carry `error_type` and nothing else, through the file's existing `_log` swallow.
- Every behaviour change lands with a row that fails when the change is reverted, and each new gate is mutation-verified with files restored from scratchpad backups (never `git checkout --`, which would discard the patch under review).

**Block If:**
- Tracking focus turns out to require a signal the `PanelWindow` seam does not carry — i.e. `focus`/`blur` are not both delivered through `events` as raw names.
- Keeping the `minimize`/`restore` pair symmetric turns out to need the window re-read at the release point rather than a latch carried across it — the `PanelWindow` seam carries no query and the Never list forbids widening it, so a design that depends on one cannot be built here.
- The latch cannot be made to leave the load-bearing `restore` row standing: if there is no rule under which a `show()` parked with a `hide()` queued behind it still swallows its `restore` echo, the guard's whole justification is gone and this is not the change that rewrites it.

**Never:**
- Do not change the `close` arm: DW-12 landed it, it already bypasses `_reconcile`, and its rows pin that absence.
- Do not change the `PanelVisibility` port (`lib/src/domain/panel/panel_visibility.dart`) — it is AD-8 verbatim — and do not widen the `PanelWindow` seam. `focus` already reaches the adapter as a raw event name.
- Do not resolve DW-30 (a `restore` starting a fresh AD-18 session) or DW-27 (a blur caused by a child window the panel itself opened). Both need a port distinction this change does not introduce. **The symmetric pair above deliberately does not touch DW-30**: it makes `minimize`/`restore` behave during one of our requests exactly as they already behave outside one, so whatever DW-30 decides a `restore` means for the session applies to both timing windows unchanged. A believed pair therefore still emits `false` then `true` on `changes`, and `CorrectionController._beginSession` still discards the user's typed text — DW-30's live defect reaching one more timing window and no wider. Ruled acceptable by the human on 2026-08-19 on that ground, and DW-30 is the next piece of work; do not attempt to suppress the emission here, which would redefine AD-18.
- Do not edit `_bmad-output/implementation-artifacts/deferred-work.md` (the orchestrator records resolution), never hand-edit `SPEC.md`, and leave `_bmad-output/specs/` untouched — including story 5, whose `<intent-contract>` I/O row this change widens. The widening is recorded here, not by editing a frozen story.

### 2026-08-19 — Escalation resolution (amends `<intent-contract>`; human decision)

Resolves the CRITICAL escalation of 2026-08-15 (`Review Triage Log` → *Second follow-up review pass*), which halted on an intent gap: an unconditional `minimize` and a guarded `restore` cannot both hold. Decided with the human in a `bmad-loop-resolve` session; nothing here is an engineering call.

- **The gap.** The contract asked for `minimize` on the structurally-external side and `restore` on the guarded side. In the baseline both are guarded, so the pair is symmetric and self-cancelling; the split made it asymmetric, and a `minimize`/`restore` pair arriving during one of our requests left the mirror false over a mapped window **permanently**. `_setMirror(false)` clears `_focused` and the `focus` arm's `_visible` guard cannot re-arm it over a false mirror, so CAP-14's dismissal died for that panel's life; and with `setSkipTaskbar(true)` the only route back is a hotkey press that reads as a summon, discarding whatever the user had typed into a panel still on screen. Reproduced in an isolated worktree and mutation-confirmed as introduced by the split.
- **The decision — symmetry, restored by a one-shot latch.** A believed `minimize` arms a latch; the next `restore` consumes it and moves the mirror back whatever `_outstanding` reads; every other `restore` keeps the guard; and our own `show()`/`hide()` clear the latch where the intent is expressed. Encoded in the Approach, in a new Always bullet, in the I/O matrix (four rows added, the `Restore during a request` row's precondition made explicit), in execution steps 1 and 5, and in three acceptance criteria. **The load-bearing row is unchanged**: a `show()` parked with a `hide()` queued behind it has already cleared the latch, so that `restore` is still swallowed and the queued hide still runs.
- **Why this does not trip the old Block If, which is now replaced.** The old condition reserved any change to `restore` for DW-30. The human's ruling is that the latch is not DW-30's question: it makes the pair behave *during* one of our requests exactly as it already behaves *outside* one, so it neither answers nor forecloses what a `restore` means for the session. The two Block If conditions now standing are the ones that would genuinely stop this design — needing a window query the seam does not carry, and losing the load-bearing `restore` row.
- **Accepted residual, explicitly ruled on.** A believed pair emits `false` then `true` on `changes`, and `CorrectionController._beginSession` (`correction_controller.dart:335-341`) clears the editor and re-seeds from the clipboard on every `true` — so a minimise-and-restore discards the user's typed text. That is DW-30, **already live today** in the nothing-outstanding case; this change extends it to one more timing window and no wider. The human ruled it acceptable on that ground and set DW-30 as the next piece of work. Suppressing the emission inside this change is forbidden — it would redefine AD-18 rather than implement DW-30's three-way rule.
- **The saved attempt patch is not restored.** `dw-31-panel-window-event-reconciliation-attempt.patch` is the defective split itself; it is evidence, not a starting point. The re-drive is from scratch against this corrected contract. Its DW-32 and DW-33 halves are unaffected by this resolution and the patch remains readable for them.

## Design Notes

**Why `minimize` is structurally external and `restore` is not.** Both come from the same GTK `window-state-event` handler (`window_manager-0.5.2/linux/window_manager_plugin.cc:1022`, `:1024`), so the symmetry is tempting — but the asymmetry is real and one-directional: `windowManager.show()` deiconifies as part of its own implementation, so our own request can produce a `restore`; nothing this adapter calls iconifies, so nothing it calls can produce a `minimize`. The split is by what our calls can cause, not by which signal the event came from.

**Why the deferred blur re-checks focus and not only `_visible`.** DW-32's decision names `_visible`. Focus has to be re-checked as well because the round trip that suppressed the blur ends in `focus()` — `gtk_window_present` — which takes the keyboard back and emits a `focus`. Dismissing after that would take down a panel the window manager has just handed the keyboard to, which is DW-33's defect reached through DW-32's door.

**Why the focus flag is cleared when the mirror goes false.** Otherwise a hidden-then-shown panel carries a stale "we hold the keyboard" from its previous life, and the first spurious `blur` dismisses it — exactly what DW-33 exists to stop. The cost is the mirror image: if the mirror goes false while the window really is mapped and focused, a later genuine blur is ignored and CAP-14 misses one dismissal. That direction is the acceptable one, and the doc says so.

Shape of the three pieces:

```dart
case 'focus':
  // Believed whoever caused it: our focus() and the user clicking the panel
  // both mean the window really holds the keyboard, so there is no echo to
  // guard against here — this is not the mirror.
  _focused = true;
case 'minimize':
  _setMirror(false); // structurally external: nothing we call iconifies

void _onBlur() {
  final heldFocus = _focused;
  _focused = false;
  if (!_visible || !heldFocus) return;         // DW-33
  if (_outstanding > 0) { _deferredBlur = true; return; }  // DW-32
  _dismiss('focus-loss');
}
```
