**The grab sequence, in the order that makes the failure readable.** Run it in the helper isolate,
on the private `Display`:
1. install `XSetErrorHandler(trap)` — the trap records `(error_code, request_code)`;
2. clear the trap;
3. for each of the four ignored modifier states, call `XGrabKey(display, keycode, modifiers | state,
   root, ownerEvents: true, GrabModeAsync, GrabModeAsync)`;
4. `XSync(display, discard: false)` — the trap has fired by the time this returns; that synchrony is
   the whole of HOTKEY-01;
5. if the trap saw `BadAccess` (error code `10`, request `33`) for the **base** modifier state,
   refuse: another client owns it. If it saw `BadAccess` only for a lock variant, keep the grab and
   log the degradation;
6. on refusal, `XUngrabKey` every state that was successfully taken, so nothing is left half-held.

**The four ignored modifier states are `{0, LockMask, Mod2Mask, LockMask|Mod2Mask}`** —
`LockMask == 1 << 1` (CapsLock) and `Mod2Mask == 1 << 4` (NumLock by near-universal convention). X
matches modifier state **exactly**, so a bare grab silently stops working the moment NumLock is on.
The four are independent grabs and do not conflict with each other (measured). Mask both bits out of
the incoming event's `state` when matching a `KeyPress`. Record `Mod2Mask == NumLock` as a documented
assumption in the code (flagged assumption A2); the robust form discovers it with
`XGetModifierMapping` + `XKeysymToKeycode(XK_Num_Lock)`, and taking that route instead is acceptable
and preferable if it proves cheap.

**Key resolution.** Take `grab.usbHidUsage`, map it to a label through `HotkeyKeyCatalogue`, then to a
keysym name through `XdgShortcutTrigger.keysymNameFor`, then to a keysym with `XStringToKeysym` and a
keycode with `XKeysymToKeycode`. **Do not build a second name table** — that is the whole DW-41/DW-43
lesson, and `keysymNameFor` is already measured against xkbcommon 1.6.0. A keysym name that is
unknown, or a `XKeysymToKeycode` that returns 0, is a refusal detected before any grab is attempted.

**The event loop** runs in the helper isolate: `XPending` → `XNextEvent`, handling `KeyPress` (post a
message down the `SendPort`) and `MappingNotify` (type `34` — call `XRefreshKeyboardMapping` and
re-grab, because keycodes are not stable across layout changes). Never block `XNextEvent` on the
Flutter isolate; that freezes the UI. The isolate exists precisely so the blocking read stays off it
and AD-8's allocation-free press path is untouched.

**Every failure is a value, never an exception, above this file** (AD-12, AGENTS.md §8). Inside the
seam, `grab()` **rejects** — that is the seam's declared contract and `X11GlobalHotkey` is what turns
a rejection into a `HotkeyBindOutcome`. Reject for: an unresolvable `libX11.so.6`
(`DynamicLibrary.open` throws `ArgumentError`, caught at first grab, not at construction);
`XOpenDisplay(NULL)` returning `nullptr`; an unknown keysym name; a zero keycode; and `BadAccess` on
the base modifier state. Preserve the disposed-mid-grab behaviour the shipped seam has and that
`test/infrastructure/hotkey/x11_global_hotkey_test.dart:434-445` describes in prose: notice disposal
after the grab lands, **undo the registration**, then throw — the adapter's error branch is the one
that race actually takes in production, and it must keep taking it.

**`release()` is a no-op when nothing is held and rejects once disposed** — unchanged from the seam's
declared contract, and `XUngrabKey` on a grab that was never held is idempotent (measured).
