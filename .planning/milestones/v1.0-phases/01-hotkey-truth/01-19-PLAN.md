<objective>
Two record defects on the capture path, in a phase whose whole subject is not saying something
false about the machine.

**WR-08 — a refusal that can never fire, and the fork this plan has to settle.** Measured, not
inferred: running `HotkeyKeyCatalogue.registrableKeys()` in this container prints
`total=63 withoutPortalTrigger=0 missing=[]`, because the flag is
`XdgShortcutTrigger.keysymNameFor(label) != null` and the two vocabularies are identical by
construction — 26 letters, 10 digits, F1–F12, and the same 15 named keys in
`HotkeyKeyCatalogue._namedKeys` and `XdgShortcutTrigger._namedKeysymNames`. So the guard in
`hotkey_capture.dart:154` is an always-false predicate, and the branch, the refusal enum value
and the user-facing sentence it renders are unreachable dead code no test can reach. This is
the same defect plan 01-07's own `resolution:` says it removed elsewhere — *"an always-false
predicate leaves branches that can never run, which AGENTS.md §1 rules out"* — so the phase
contradicts its own standard inside its own code.

01-REVIEW.md offered two ways out and 01-VERIFICATION.md says the plan must choose one and say
why. **This plan chooses (a): delete the field, the enum value and the branch.** The reason,
and it is a measurement rather than a preference: the divergence the guard exists to catch is
already asserted **three times**, in both directions, by rows that fail at build time with a
developer-readable reason —

- `xdg_shortcut_trigger_test.dart`, "every key label the X11 catalogue offers has a Wayland serialization" — every `HotkeyKeyCatalogue.labels` entry resolves to a keysym name;
- the same file, "and this table offers no label the X11 catalogue lacks" — the other direction, plus `XdgShortcutTrigger.labels == HotkeyKeyCatalogue.labels`, same labels and same order;
- `hotkey_key_catalogue_test.dart`, the loop over `registrableKeys().all` asserting the flag on every key.

A guard that is strictly dominated by three existing assertions is not a safety net; it is dead
code with extra steps. And the two failure modes are not equivalent: a divergence caught by a
test stops the build in front of the developer who caused it, while a divergence caught by this
branch reaches a *user* as a refusal sentence about a key they just pressed. Deleting loses
nothing, because the guarding was never being done by the field. What it gains is that
`HotkeyCaptureRefusal`'s own doc — *"One value per subject, so the surface renders one reason
per cause"* — becomes true of every value it has, and the sealed-type discipline this codebase
relies on stops carrying a case no surface can ever be asked to render.

**WR-07 — a measured fact still flagged as an open unknown.** Both AltGr comments still read
that the mapping was not verified, after UAT test 9 settled assumption A3 by **live
observation** on an `altgr-intl` layout — the refusal rendered, the shortcut not folded into
Alt — and `settings_screen_hotkey_test.dart:744-820` pins it. A stale flag tells the next
reader to treat a measured fact as open and invites re-doing finished work. Open across two
consecutive reviews; UAT test 9 itself says the notes "can now be updated".

Output: a capture validator with four reachable refusal subjects and no unreachable fifth, and
two comments that say what was measured.
</objective>
