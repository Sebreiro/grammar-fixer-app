<objective>
Replace the key-label text field with a capture control the user presses their combination into, and
move the validation forward from Apply to capture.

Purpose: HOTKEY-04 was written as *"curate the settings key field against `HotkeyKeyCatalogue` so the
seven labels that bind on Wayland but are refused on X11 cannot be entered by name."* Two things
changed under it.

**First, D-14 removes entry by name entirely.** The user presses the combination; they never have to
know their key is called `Pause` or `ISO_Level3_Shift`. So the requirement becomes *validate what was
captured* rather than *curate what can be typed*. Same goal: the user cannot end up with a shortcut
that does not fire.

**Second — and this corrects the premise CONTEXT.md states — the seven labels dissolve.**
`labelsThatBindTheWrongKey` = `{Space, Tab, Enter, F1, F2, F3, F4}` is an artefact of the removed
vendor plugin's own reverse-lookup table (`uni_platform` scanning Flutter's `kGtkToLogicalKey` and
taking the first match, which lists keypad/ISO/3270 variants first) — **not** of X11, not of
keybinder, not of GTK. Measured three ways on 2026-09-01 against the installed `libX11.so.6`,
`libgdk-3.so.0` and `libgtk-3.so.0`, plus a real keycode round trip on `Xvfb :77`:
`XStringToKeysym("space")` → `0x20`, `"Tab"` → `0xff09`, `"Return"` → `0xff0d`, `"F1"` → `0xffbe`,
`"F4"` → `0xffc1`; `gtk_accelerator_parse("<Control><Shift>space")` → `keyval=0x0020`. No `KP_Space`,
no `ISO_Left_Tab`, no `3270_Enter`, no `KP_F1`–`KP_F4` anywhere. With the plugin gone (plan 01-02) and
keys resolved by keysym name, all seven bind correctly. The set becomes **empty** and every
special-case for it goes.

So D-15's reject-at-capture needs a different subject, and it has five real ones — enumerated in Task
2. The validator survives; its role changes.

Output: a capture control, a catalogue that validates instead of allowlisting, and a vocabulary the
`ui` ring reads through the controller rather than across AD-1's rings.
</objective>

**The vocabulary route is already ratified — do not re-litigate it.** DW-71's `decision:`
(2026-08-14, ledger line 1182): *"Expose the catalogue through a port — engineering call, taking the
non-destructive option. The ui ring gets a sanctioned way to read which labels this build can
register — **supplied by `SettingsController`** rather than reached for across AD-1's rings —
validated before Apply."*

**What "supplied by `SettingsController`" cannot mean, read off the gate (verified 2026-09-01).**
`test/architecture/ad1_import_rule_test.dart` runs *four* rules, and the second is
`test('AD-1: lib/src/application/** never imports infrastructure')` at `:60`, whose reason string
reads *"application files may reference only dart: libraries, Riverpod (AD-17), and paths inside
lib/src/application/ or lib/src/domain/"*. The ui rule at `:93` is the same shape. Both run
`_directiveUris` — a scan of every `import`/`export`/`part` URI — so the *import* is what fails, in
either ring. A controller that imported the catalogue to supply it would fail the application rule
just as loudly as a widget importing it fails the ui rule. `grep -rn 'infrastructure' lib/src/application/`
returns three hits today and **all three are doc comments**; the ring has never imported across.

**So the route is composition-root injection, and the shape already exists.** `port_providers.dart`
states it in its own library doc (`:1-22`): *"every provider here is declared over a domain port and
throws until it is overridden, and `main.dart` — which lives outside `lib/src/` and so outside the
AD-1 gate — is the only file that supplies an override, so it is the only place a concrete adapter is
bound to a seam."* Ten seams follow that pattern (`loggerProvider` … `activePresetProvider`), each
`Provider<DomainType>((ref) => throw UnimplementedError('main.dart must override …'))`, and
`controller_providers.dart:50-57` is where `SettingsController` is constructed from them.

**The parity gate that comes with it.** `composition_wiring_test.dart:20-48` asserts both directions:
`declared.difference(overridden)` must be empty (a seam with no override) **and**
`overridden.difference(declared)` must be empty (an override for a dead seam). It is generic over the
scan, so adding a seam *and* its override keeps it green with no edit to that file — but adding only
one half turns it red.

What Flutter gives the capture, and it is better than CONTEXT.md assumes: `KeyEvent.physicalKey` is a
`PhysicalKeyboardKey` whose `usbHidUsage` is *exactly* the integer `HotkeyKeyCatalogue` is keyed on
and that `HotkeyGrab` carries. So the capture reads `event.physicalKey.usbHidUsage` and looks it up
directly — no label guessing, no layout dependence, and a dead key still has a physical location.
`HardwareKeyboard` supplies the regularized sequence: one `KeyDownEvent`, zero or more
`KeyRepeatEvent`s, one `KeyUpEvent`, all with the same physical and logical key.

  <decision>On X11, while the daemon holds a passive grab on the current shortcut, that combination cannot reach the focused settings window. What should the user experience when they press their current shortcut into the capture control?</decision>
  <context>
    This is a user-visible behaviour that D-14 and D-16 do not cover, and no in-tree analog settles it.

    A passive grab means the X server delivers the combination to the grabbing client, not to the
    focused window. So a user who opens Settings and presses their *existing* shortcut into the
    capture control gets one of two things depending on how the app is built: nothing at all (the
    capture sits there looking broken), or the panel toggles under them (because the grab fired and
    the daemon did what the shortcut says).

    This is entirely plausible behaviour for a user to attempt — re-entering the shortcut you already
    have is what people do when they are checking the control works, or re-applying after a failure.

    [Flagged assumption A4: this follows from X11 passive-grab semantics and was **not** reproduced in
    this session. It is reproducible under `Xvfb` in this container if you want it settled first — the
    grab and delivery paths were both proved there during research.]

    Wayland is unaffected: the compositor owns the binding and ordinary key events still reach a
    focused settings window.
  </context>
  <options>
    <option id="release-during-capture">
      <name>Release the grab for the duration of the capture, and re-take it when capture ends</name>
      <pros>The control behaves identically for every combination, including the current one. No special case in the UI, and nothing the user can press produces silence.</pros>
      <cons>The shortcut does not work while the settings screen is capturing — a window of seconds where pressing it does nothing. If capture is abandoned by a crash or an unhandled path, the grab must still be restored, which is a new lifecycle obligation on a path that currently has none.     </option>
    <option id="treat-silence-as-current">
      <name>Treat "no key event arrived" as "that is already your shortcut"</name>
      <pros>No grab lifecycle change and no window where the shortcut stops working. The panel toggling is arguably a *correct* answer to the user — it demonstrates the shortcut works.</pros>
      <cons>Requires a timeout heuristic to distinguish "you pressed your current shortcut" from "you pressed nothing", and a heuristic that guesses wrong tells the user something false. The panel opening on top of Settings mid-capture is confusing on its own terms.</cons>
    </option>
    <option id="explain-in-place">
      <name>Do nothing special; the capture shows a standing hint that the current shortcut cannot be re-captured, and offer a plain "keep current" affordance</name>

**Add the validator, whose five subjects are all real** (RESEARCH.md § "HOTKEY-04 after the
replacement"). Each returns a distinct, user-facing reason — D-15 requires the reason, not just the
refusal:
1. **No modifier at all** (D-13, unconditional). A global grab takes the key from every application,
   and a user who binds bare `G` loses the letter system-wide — in an app built for people writing
   English text. Not even function keys are exempt.
2. **A modifier-only press.** `Ctrl` alone, or `Shift`+`Ctrl`: there is no key to grab.
3. **A key outside the catalogue.** `usbHidUsageFor(label) == null`. `X11GlobalHotkey._bind` already
   refuses these before the backend (`:112-124`), and `XdgShortcutTrigger` cannot express them either
   — so the user would apply, wait, and be told no. D-15 moves that answer to capture time.
4. **An AltGr / Level-3 combination.** `HotkeyModifier` has exactly four values —
   `{control, alt, shift, meta}` — and no value for Level 3, so the combination cannot be represented
   at all. It must be **refused**, never folded into `alt`: folding produces a shortcut whose
   serialization is a plain Alt combination that fires on a different physical key.
5. **A combination whose portal trigger cannot be built.** `XdgShortcutTrigger.keysymNameFor(label)`
   returns null, so on Wayland the hint would be omitted and the compositor would pick something
   else — a shortcut that silently is not the one the user chose.
