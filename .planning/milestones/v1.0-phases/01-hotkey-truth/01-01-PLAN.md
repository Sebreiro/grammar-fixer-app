    Nothing in this phase's *code* changes either way — Flatpak is in both sets, and Flatpak is the
    only member that changes the portal handshake. What changes is what the ledger records and what
    the (deferred) packaging phase is committed to building.

    Three further facts the human should have before answering:

    1. **The narrowest permission set that works (D-19) needs almost no `finish-args`.** Flatpak's
       default sandbox already gives a writable `~/.var/app/$FLATPAK_ID`, and
       `org.freedesktop.portal.*` bus names are allowed by default, so the GlobalShortcuts portal
       needs no grant at all. Clipboard comes with the display socket. The measured minimal set is
       `--socket=wayland`, `--socket=fallback-x11`, `--share=ipc`, and — for Phase 6's API key only —
       `--talk-name=org.freedesktop.secrets`. **No `--filesystem=` of any kind.**
    2. **The load-bearing cost D-18 and D-19 do not mention.** The shipped default correction
       provider is three processes deep: daemon → Python sidecar → `claude` CLI, and the spine's
       envelope (`ARCHITECTURE-SPINE.md:583`) lists a Python 3.11+ interpreter with
       `claude_agent_sdk` **plus** the `claude` CLI on `PATH` as runtime dependencies the app cannot
       supply itself. Inside a Flatpak sandbox neither host binary is reachable. Making the Flatpak
       actually work therefore needs either both bundled into the runtime, or a host escape
       (`--talk-name=org.freedesktop.Flatpak` + `flatpak-spawn --host`) — and the second is the
       opposite of D-19's commitment. This does not block Phase 1, but it materially changes what
       "ship a Flatpak" costs. [Flagged assumption A6: that no bundling work exists today was
       reasoned from `assets/sidecar/` shipping as a Flutter asset and `tool/provision_sidecar.sh`
       creating a `.venv-sidecar/` outside the bundle — not verified end to end.]
    3. **Building the pipelines is explicitly deferred** (CONTEXT.md § Deferred Ideas). This decision
       commits to formats, not to manifests.
  </context>

  <decision>How does the `GlobalHotkey` port expose what is bound right now, and does the same member carry the compositor's own description text?</decision>
  <context>
    D-01 requires the app to display the shortcut *currently in effect*, silently, and never the
    combination it requested. A tray daemon spends almost all its life with no settings screen
    mounted, and `bindingChanges` is a broadcast stream with no replay — so every compositor rebind
    that happens while the screen is closed is dropped, and AD-10 then renders the stale startup
    `bind()` result. That is FLAT-02, and AD-8 already solves the identical shape for the panel by
    pairing a synchronous `bool get isVisible` with `Stream<bool> get changes`.

    **The count the roadmap and CONTEXT.md both understate.** The roadmap names one AD-9 declaration
    edit in this phase; CONTEXT.md's D-06 says there is a third. Research found **four**. Three of
    them are *additions* that leave every declared field and constructor untouched — squarely inside
    the recorded precedent. Only two need fresh ratification, and they are gated at the head of the
    plans that make them (`HotkeyUnavailable`'s cause in plan 01-04, `HotkeyBinding`'s `const` in
    plan 01-09). This checkpoint settles the additive one, and whether HOTKEY-03's description
    carrier folds into it.

    **Why folding matters.** HOTKEY-03/D-04 needs the portal's localized `trigger_description` to
    reach the `ui` ring, where today it goes only to a log line
    (`wayland_portal_global_hotkey.dart:1120-1141`). Carrying it as a third declared field on
    `HotkeyRegistration` or `HotkeyBound` would be a *declared-field-list* edit needing its own fresh
    ratification. Carrying it on a brand-new type reached through one new member is an *addition*.
    Choosing option `status-type` collapses two gates into one.

    **What must not be chosen, and why (D-05, and the spec).** No field of any GlobalShortcuts reply
    carries a machine-readable combination — `description` and `trigger_description` are the only
    shortcut properties in the Response, `ListShortcuts` reply and `ShortcutsChanged` signal. So the
    read-back is real (the app reads the portal's report rather than its own request) but it cannot
    be parsed into a `HotkeyBinding`. Any option that promises a structured Wayland combination is
    promising something the protocol does not carry.

    **A synchronous read must not perform a round trip.** HOTKEY-06 exists precisely because a
    late-mounting settings screen must not await one.
  </context>
