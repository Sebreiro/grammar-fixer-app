<objective>
Close the second half of the tracer's promise: **a refused grab no longer costs the user the shortcut
that was working.** D-10 states it as a product rule — *"On X11, a combination another application
already owns is refused, and the previously working shortcut stays in effect. They never lose a
working shortcut they did not ask to give up."*

Purpose: this is a defect the source artifacts did not surface, found by reading the shipped adapter.
`X11GlobalHotkey._bind` calls `_releaseBeforeRebinding()` *before* it attempts the new grab, and that
helper sets `_effective = null` with the comment *"Past here nothing is held: a grab that fails must
not leave the old combination reported as effective, because it is not."*
(`x11_global_hotkey.dart:314-316`). The comment is honest — the code really does drop the working
shortcut on the way to failing. So today, when another client owns the requested combination, the
user loses a shortcut they never asked to give up, and gets `HotkeyUnavailable` for their trouble.

**The reason that ordering existed evaporates with plan 01-02.** The old seam had to release first
because the vendor plugin's `std::map::insert` does not overwrite, so grabbing over a live
registration left the backend holding two — one press firing twice, AD-8's toggle showing and
immediately hiding, the panel appearing never to open. `X11KeyGrabRegistrar` owns its grab set
explicitly, X allows a client to hold several passive grabs at once, `BadAccess` is synchronous, and
`XUngrabKey` is idempotent (all measured against a live `Xvfb :77`, 2026-09-01). So the new registrar
can acquire the new combination, confirm it, and only then let the old one go.

Output: a bind path where refusal is non-destructive, and the adapter's own `_refusedBeforeBackend`
rule — which already says exactly this for the before-the-backend cases — extended to the case the
backend actually answers.
</objective>

Move the release from *before* the acquisition to *after a confirmed* acquisition, in both files, so
that a refusal is observed while the previous grab is still held.

**In `x11_key_grab_registrar.dart` — make `grab()` an atomic swap.** Today plan 01-02 left it
following the old seam's shape: release whatever is held, then acquire. Invert it:
1. Resolve the requested combination to a keycode **before** touching any existing grab. An
   unresolvable keysym name or a zero keycode is a refusal detected with nothing disturbed.
2. Acquire the new grab — all four ignored modifier states, under the error trap, then `XSync`.
3. If the base modifier state came back `BadAccess`, ungrab whichever of the four states were
   actually taken and **reject**, leaving the previously held combination exactly as it was. Nothing
   was released.
4. Only once the acquisition is confirmed clean, `XUngrabKey` the previously held combination and
   record the new one as held.

Two edge cases the sequence must name explicitly, because both are reachable:
- **Re-grabbing the combination that is already held.** X will report `BadAccess` for a client
  grabbing a combination *it already holds itself*, which would make an idempotent rebind look like a
  conflict. Detect this before step 2 by comparing against the recorded held combination, and treat
  it as already-satisfied: ungrab nothing, acquire nothing, resolve successfully. Do **not**
  short-circuit on the *requested* binding the way a naive equality check would — short-circuiting on
  the request is what the old `_releaseBeforeRebinding` doc explicitly refuses, because it "blocks
  every recovery path: a binding that was refused, or lost, could then never be asked for again."
  Compare against what is *held*, which is only ever set after a confirmed acquisition, so a binding
  that was refused was never recorded as held and can always be re-requested.
- **A lock-mask variant refused while the base state succeeded.** Keep the grab, log the degradation
  naming which state failed, and resolve. The user's shortcut works; it will not fire while that one
  lock is latched. That is a strictly better outcome than refusing outright, and it is the
  documented behaviour plan 01-02 already carries.

Update the `grab()` doc on `hotkey_registrar.dart` to state the new guarantee in the seam's own
terms: a rejected `grab` has released nothing, so whatever was held before the call is still held. The
current text says the opposite ("releasing whatever was held first"), and that sentence is what
`X11GlobalHotkey` is written against.
