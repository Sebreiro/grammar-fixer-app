<objective>
State which of the port's two writers wins when they disagree, and make the rebind path obey the rule
the startup path already does.

Purpose: `bind()`'s returned outcome and the `bindingChanges` stream are two writers of one piece of
state with no stated precedence. The GlobalShortcuts documentation specifies no ordering between the
`BindShortcuts` Response and `ShortcutsChanged`, so both orderings are spec-legal and a second
adapter — or a future one — could implement the opposite order and still satisfy every written
invariant (FLAT-03).

**The application ring currently implements three contradictory rules**, verified against the shipped
code:

| Path | Rule today | Where |
|---|---|---|
| Startup | **Newest wins.** `applyStartupOutcome` refuses to overwrite an outcome that is already set, precisely because a compositor change can land first. | `settings_controller.dart:294-312` |
| Backend-originated change | **Last writer wins**, unconditionally. | `:324-333` |
| User rebind | **`bind()` wins**, unconditionally, with no check for a newer event. | `:142-172` |

So a `ShortcutsChanged` that arrives *while* a user-initiated bind is in flight — and a portal dialog
makes that window seconds wide by design — is silently overwritten by the bind's own answer. That is
the same defect `applyStartupOutcome` was written to prevent, on the path that is easier to reach.

**One honest scoping note.** `_listenForShortcutSignals` is called *after* `_bindShortcut` returns
(`wayland_portal_global_hotkey.dart:319-321`), so on the shipped adapter a `ShortcutsChanged` cannot
be observed before the `BindShortcuts` Response — the subscription does not exist yet. The inversion
is **possible in the protocol and unreachable in this implementation**. Say so; do not claim a defect
that cannot occur here. What *is* reachable is the rebind window above, and that is what the guard
closes.

Output: the rule written where both writers are declared, and the guard on the path that lacked it.
</objective>

```dart
  /// A **seed**, not an assignment: it applies only while nothing is known yet.
  /// The startup bind is not the only thing that can resolve first — the Wayland
  /// adapter subscribes to `ShortcutsChanged` inside `bind()`, so a
  /// compositor-originated change can reach [bindingChanges] and land here before
  /// `bindHotkey`'s own answer is handed over. Overwriting unconditionally would
  /// replace that newer fact with an older one, and nothing would emit again to
  /// correct it.
  void applyStartupOutcome(HotkeyBindOutcome outcome) {
    if (_state.hotkeyBindOutcome != null) {
      _log(() => _logger.info(
        'the startup bind outcome was not applied because the surface '
        'already holds a newer one',
      ));
      return;
    }
    _setState(SettingsState(…));
  }
```

The two paths that contradict it — same file:
```dart
  // :324-333 — last writer wins, unconditional
  void _onBindingChanged(HotkeyBindOutcome outcome) { _setState(SettingsState(…, hotkeyBindOutcome: outcome, …)); }

  // :142-172 — bind() wins unconditionally, with no check for a newer event
  Future<void> changeHotkey(HotkeyBinding binding) async {
    if (!_beginMutation()) { return; }
    try {
      final (outcome, bindFailure) = await _bind(binding);
      final writeFailure = await _writeChange((config) => config.copyWith(hotkeyBinding: binding));
      _setState(SettingsState(config: _currentConfig(), hotkeyBindOutcome: outcome, …));
    } finally { _endMutation(); }
  }
```

The mechanism already available: `_mutating` is a field *beside* the state because `_beginMutation`
must answer synchronously (`:117-123` doc). A generation counter or a latch set by
`_onBindingChanged` during a mutation fits the same slot.

**The rule to state:**

> `bind()`'s returned outcome is authoritative **only for the transition it caused, and only until a
> backend-originated change is observed.** A `bindingChanges` event observed at any time after a
> `bind()` was issued supersedes that `bind()`'s return value, whichever resolves first in wall-clock
> order. Concretely: a consumer records a generation number when it issues a `bind()`, and discards
> the bind's outcome if a `bindingChanges` event arrived after that number was taken.

**The rationale to state with it**, because a rule with no reason gets re-litigated: on Wayland the
compositor is the authority (AD-10) and D-01 requires the app to show what is *currently* in effect.
A stale `bind()` answer is by construction older than any backend-originated change the backend
emitted afterwards.

**State the boundary honestly, in the same doc.** The protocol permits `ShortcutsChanged` before the
`BindShortcuts` Response and the documentation states no ordering — but the shipped Wayland adapter
subscribes to the signal only *after* the bind returns
(`wayland_portal_global_hotkey.dart:319-321`), so that particular inversion is unreachable here today.
The rule exists because a second adapter, or a change to that subscription order, would make it
reachable — and because the rebind window it also covers is reachable now. Do not write the doc as if
it were fixing a live inversion at startup; that would be a claim the code does not support.

**Say what "observed" means**, since the whole rule hangs on it: the moment the consumer's
`bindingChanges` listener runs, not the moment the backend emitted. A consumer can only order what it
saw.

**The mechanism.** Record a generation number when the bind is issued; increment it in
`_onBindingChanged`. After `await _bind(binding)` returns, compare: if a backend-originated change
arrived after the number was taken, **discard the bind's outcome** and leave the state holding the
newer one. Otherwise apply the bind's outcome exactly as today.

A counter is preferable to a boolean latch because two changes during one mutation must not read as
none, and because the same counter is what a future consumer needs to implement the rule Task 1
documented.

**Where the counter lives.** Beside the state, not in it — the same slot `_mutating` occupies, and for
the same reason its doc gives: `_beginMutation` must answer synchronously. Do not put it on
`SettingsState`; it is bookkeeping, not something a consumer renders.

**Log the discard.** `applyStartupOutcome` logs when it declines to apply, at info level, and this
path should say the same kind of thing: the rebind's own answer was not applied because a newer
backend-originated change had already landed. A silent discard is the failure mode this whole
requirement is about, one level up.

**Break the tie toward the backend.** If a change lands in the same turn as the bind's answer, the
backend wins. The rule Task 1 wrote is "a `bindingChanges` event observed at any time *after* a
`bind()` was issued supersedes" — a same-turn arrival is after the issue, so it supersedes. Make that
explicit in the comparison rather than leaving it to operator choice, and say so in a comment.

**Do not change `applyStartupOutcome`.** Its seed-not-assignment rule is already correct and its doc
already explains why. Leave it exactly as it is.

**Do not change `_onBindingChanged`'s last-writer-wins semantics.** Between two backend-originated
changes, the later one is genuinely newer and should win. What changes is only that it now bumps the
generation.

**Coordinate with Phase 2, do not collide.** SETTINGS-02 (DW-68) also edits `changeHotkey` — it closes

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| two writers → one state field | The bind's return value and the backend's change stream both write what the user is shown. Ordering between them is not guaranteed by the protocol. |
| compositor → application ring | A backend-originated change is a fact the app did not cause and cannot re-derive. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-42 | Repudiation | `changeHotkey`'s unconditional write | high | mitigate | A stale bind answer overwriting a newer compositor change leaves the user looking at a shortcut that is not in effect, with nothing left to emit a correction — the compositor already sent its one event. The generation guard closes it, and the discard is logged so the case is observable rather than silent. |
| T-01-43 | Tampering | an unwritten ordering rule | medium | mitigate | With no stated precedence, a second adapter could implement the opposite order and still satisfy every written invariant, so two builds of the same app would disagree about what the user sees. Writing the rule in the port — where both writers are declared — is the control. |
| T-01-44 | Denial of service | a change lost during a seconds-wide portal dialog | medium | mitigate | The rebind window is seconds wide by design on Wayland, which is exactly why this is the reachable case rather than the theoretical one. The guard covers the whole `await`, not just the moment of assignment. |
| T-01-45 | Information disclosure | the discard log line | low | mitigate | The log names the situation, not the binding: no key label, no combination, no user text. Follows `applyStartupOutcome`'s existing decline-log shape, which carries no context map at all. |
