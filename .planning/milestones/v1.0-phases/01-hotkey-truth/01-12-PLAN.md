<objective>
Stop the daemon dismissing its own panel on its own shortcut, by asking the one question the seam
was missing: **did the keyboard actually go anywhere?**

Purpose: G-01-13's root cause is an AND-gate. (1) The daemon's passive grab activating makes X send
`FocusOut(mode=NotifyGrab)` to the focused window — the panel — and `window_manager 0.5.2` reports
that as a bare `blur` with the X focus mode discarded
(`window_manager_plugin.cc:979-982`, `:1108`), so `_onBlur` answers it with a real `hide()`.
(2) That hide beats the toggle's own activation by 4-12 ms, so `onHotkeyActivated()` reads a mirror
that already truthfully says hidden and re-shows the panel it just dismissed.

Break either condition and the toggle works. This plan breaks the first, and breaks it with a
*fact* rather than with timing.

Output: an infrastructure-private witness seam, an X11 implementation built on one Xlib call, a null
object for every host that cannot answer, and the fourth question in `_onBlur`.
</objective>

## Why this direction, and not the other two

The debug session offered three. They are not equally priced.

**(c) Make the press path beat the GTK path — rejected.** There is no ordering guarantee to be had.
The blur travels X → GDK → platform channel → the Dart main isolate; the activation travels
X → the worker isolate's poll → an isolate message → the same Dart main isolate. Both are async and
both end on the same event queue, so removing the 8 ms poll widens a 4 ms margin without closing
anything. It also reopens T-01-09: the poll exists because a blocked `XNextEvent` cannot notice a
teardown message (`x11_key_grab_registrar.dart:585-591`).

**(a) Suppress the dismissal while the daemon's own grab is active — rejected.** The suppression
signal would have to travel the *same* worker-isolate path that already loses the race, so it
arrives after the blur it is supposed to suppress. Bridging that gap needs a latch plus a deadline,
which is the pattern AGENTS.md §6 rules out. It would also push hotkey knowledge across a seam into
the panel adapter for no other reason.

**(b) Recover the X focus mode — chosen, in a narrowed form.** Recovering the *mode* literally means
forking or patching `window_manager`, or adding native runner code plus a second platform channel —
and the second still races, because a mode arriving on channel B has no ordering guarantee against
the `blur` on channel A.

But the mode is only a proxy. CAP-14 asks *"has this window lost the keyboard?"*, and X answers that
question directly, synchronously, and without being disturbed by a grab: **`XGetInputFocus`**. A
keyboard grab does not move the input focus — that is precisely why X labels the focus-out
`NotifyGrab` rather than sending a real focus transfer. So the discriminator is not "was this a
grab?" but "is the keyboard still where it was when we last held it?", and that is race-free in both
directions: under a grab the focus never moves at all, and under a genuine focus loss the focus has
already moved before the focus-out is sent.

Two further facts that shape the implementation:

- The window `XGetInputFocus` names is `4194308`, a **child** of the daemon's toplevel `4194307`.
  So the answer is not "is the focus window our toplevel?" — it is "is the focus window the same one
  it was when the window told us it had taken the keyboard?"
- openbox's own focus window carries no `_NET_WM_PID` at all, which is one more reason not to build
  the answer out of window properties.

## The seam

Infrastructure-private, beside `panel_window.dart`, and for the reason that file already states in
its own doc: a single-implementation seam is justified when there is a real test need, and there is
one — the adapter's rows are binding-free `package:test` rows and cannot reach a real X server.

Keeping it out of `lib/src/domain/` is deliberate and load-bearing. Nothing above infrastructure
reads it; putting it there would add a domain type no ring above uses, and — the part that matters —
this fix then touches **no verbatim-frozen declaration at all**. `PanelVisibility` (AD-8) and
`GlobalHotkey` (AD-9) are untouched, so no spine ratification and no human gate stands between this
gap and its fix.

```dart
abstract interface class KeyboardFocusWitness {
  /// Records who the display server gives the keyboard to right now, so a
  /// later [focusUnmoved] has something to compare against. Called when the
  /// window reports that it took the keyboard.
  void recordFocusGained();

  /// Whether the display server still gives the keyboard to the same window
  /// [recordFocusGained] last recorded.
  ///
  /// `false` whenever this cannot be established — nothing witnessed yet, no
  /// display, a server that will not answer, or a focus the server reports as
  /// belonging to no window. A caller that dismisses on `false` therefore
  /// behaves exactly as it did before this seam existed.
  bool get focusUnmoved;

  /// Idempotent.
  Future<void> dispose();
}
```

Two members and one job. `focusUnmoved` is the whole contract: **it may only be `true` where the
absence of a focus transfer is positively established.**

## The adapter change, in full

Three edits to `window_manager_panel_visibility.dart`, and nothing else.

1. Constructor takes `required KeyboardFocusWitness focusWitness`. The adapter **owns** it, the same
   way its doc already says it owns the `PanelWindow` it is given: `dispose()` disposes it.
2. The `focus` arm of `_onWindowEvent` — inside the existing `if (_visible)` guard, beside
   `_focused = true` — also calls `_witness.recordFocusGained()`. Nowhere else.
3. `_onBlur` gains the fourth question, and the `_focused` clear moves:

```dart
void _onBlur() {
  if (!_visible) {
    _focused = false;
    return;
  }
  if (!_focused) {
    return;                       // DW-33, unchanged: it never held the keyboard.
  }
  if (_keyboardStillHere()) {
    return;                       // The focus did not move. _focused stays true.
  }
  _focused = false;
  if (_outstanding > 0) {
    _deferredBlur = true;
    return;
  }
  _dismiss('focus-loss', PanelVisibilityState.focusLost);
}
```

and `_releaseDeferredBlur` gains the same question immediately before its `_dismiss`.

`_keyboardStillHere()` is the AD-15 backstop wrapper: it returns `_witness.focusUnmoved`, and on any
throw it logs once (`error_type` only, per the Logger port) and returns `false`.

**Why `_focused` stays true on the suppressed path, and why that is not incidental.** UAT test 14's
`retest_after_fix` names a latent mechanism: presses 1 and 3 ended on `FocusIn(NotifyUngrab)` and 2
and 4 on `FocusIn(NotifyNormal)`, and if GDK ever drops the `NotifyUngrab` form, `_focused` is left
false and the next genuine blur is discarded by DW-33 — resurrecting the withdrawn G-01-14 symptom
for real. Keeping `_focused` true when the keyboard demonstrably never left removes that dependency
outright: the adapter no longer needs a focus-in to come back.

**The four mechanisms, each preserved, and the doc must say so.**
1. *The mirror leads* — untouched. The witness writes no mirror and is read only on a path that has
   already read one.
2. *Requests are serialised* — untouched. The witness never enters `_apply`'s chain and issues no
   window call.
3. *A superseded request is abandoned* — untouched. No new request exists to supersede.
4. *A window call is bounded* — the witness is **not** a window call and is deliberately not bounded
   by `_requestTimeout`. It is one synchronous X round trip on the platform thread. State the
   residual honestly in the doc: an X server that stops answering blocks it — and blocks GDK's own
   per-frame round trips on that same thread and that same server first, so this adds no new class
   of hang. That claim is reasoning, not a measurement, and must be written in that register.

**DW-33 is preserved and strengthened, not contradicted.** Its question — *did this window ever hold
the keyboard?* — stays, and stays first. The new question is orthogonal: *has the keyboard actually
gone anywhere?* A focus-out at a window that never took the keyboard and a focus-out that moved no
keyboard are two different non-dismissals.

**One behaviour change to record, deliberately.** A foreign client's global shortcut fired while our
panel is up will no longer dismiss the panel. Today it does — that is the diagnosis's smoking-gun
control. Not dismissing is the more correct answer (a foreign grab moves no focus and the panel gets
the keyboard back), but it is a change, and plan 01-13 measures it and plan 01-14 records it.

## The X11 witness

`XGetInputFocus(Display*, Window* focus_return, int* revert_to_return)` — **it takes no window
argument, so it cannot raise `BadWindow`.** That is why the read path is built from it alone and not
from a tree walk plus a property read: `XSetErrorHandler` is a process-global, and
`x11_key_grab_registrar.dart:604-634` records that the worker's trap is a `Pointer.fromFunction`
belonging to *that* isolate, so an X error raised from the main isolate while a grab batch has the
trap armed would invoke it cross-isolate — which the VM treats as fatal rather than as a stray log
line. A one-call read path closes that by construction.

Shape:
- Open the display **lazily**, on first use, not in the constructor: a witness that is never read
  holds no connection, and a startup that aborts before the panel exists leaks nothing.
- `XOpenDisplay(nullptr)` answering `nullptr` is a value, not a throw. Remember the failure and
  answer `false` for the rest of the process's life rather than retrying on every blur.
- `recordFocusGained()` stores the current focus window. Treat `None` (`0`) and `PointerRoot` (`1`)
  as "cannot answer" and store nothing — on a focus-follows-mouse server the answer would otherwise
  compare equal on every blur and suppress CAP-14 entirely.
- `focusUnmoved` re-reads and compares. No stored window, either side unanswerable, or a differing
  id ⇒ `false`.
- `dispose()` closes the display, guarded, and is idempotent — the same discipline as the recent
  `XCloseDisplay` guard (`a419249`), where a failed display open must not fault teardown.
- Free whatever is allocated for the out-parameters. This runs in a resident daemon, on every blur
  at a focused panel, all day.

`libX11.so.6` is already loaded — it is an unconditional `DT_NEEDED` of `libgdk-3.so.0`, which is
the argument phase 01 plan 01-02 already relies on. No new runtime dependency appears.

|----------|-------------|
| X display server → daemon | Focus reports and window ids arrive from a server shared with every other client on that display; X11 offers no inter-client isolation |
| GTK/`window_manager` plugin → Dart adapter | Window event names cross the platform channel with the X focus mode already discarded — the seam this gap exists in |
| worker isolate ↔ main isolate | Both map the same `libX11.so.6` and share one process-global X error handler |
