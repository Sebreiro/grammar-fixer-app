# Roadmap: Hotkey Grammar Corrector — Ledger Hardening

## Overview

This milestone hardens a shipped daemon rather than building one. Its 50 requirements are
verified-open entries of the BMAD deferred-work ledger: the hotkey, settings, panel, and teardown
surfaces are made to tell the truth about what they actually did; CAP-8 finally gets a second
provider to choose; and the spine is brought back into agreement with the code that exists.

The order is dictated by dependency. The hotkey cluster comes first, as Phase 1, because it owns
the most fragile file in the tree and because the packaging decision inside it retroactively
constrains that file. Everything else is Phase 2, where the same dependency order survives as
internal waves: the milestone's one feature-shaped requirement — the second correction provider —
is Wave E, second-to-last, because the bounded-teardown and `onDone` prerequisites in Wave D gate
it, and the spine refresh is Wave F, last, because it is honest only after the work it describes
has landed.

**Phase merge, 2026-09-14.** The former Phases 2–7 were merged into a single Phase 2 at the user's
direction. Nothing was descoped: all 40 of their requirements carry over, and the six phases
became the six internal waves A–F documented in the Phase 2 section. Criteria that covered the
same surface were merged rather than duplicated.

**Scope reduction, 2026-08-31.** The original roadmap carried 88 requirements across 10 phases.
All test, gate, CI, runtime-observation and review-pass work — 38 requirements, including the
entire Phase 1 (Gate Reality), Phase 9 (Runtime Observation) and Phase 10 (Deferred Review
Passes) — was removed outright at the user's direction as not a priority for this milestone. The
removed set is recorded in `REQUIREMENTS.md` under *Removed: Test-Shaped Work*, and the ledger
entries behind it remain `status: open` in `deferred-work.md`. Consequence on record: the 50
surviving requirements close on inspection and on the existing suite as it stands, not on a gate
that has run — `.github/workflows/ci.yml` still reads `STATUS: NEVER EXECUTED`.

**Standing constraints on this roadmap:**

- **No schema-changing work is scheduled anywhere.** Drift's v1 schema snapshot can only be
  captured while v1 is the live schema, and no v1 requirement touches the schema. A phase that
  bumped `schemaVersion` would permanently destroy the baseline every existing user is on.
- **There is no data-safety phase.** The history/sqlite cluster (file permissions, retention,
  corrupt-DB recovery, schema snapshot) is entirely `parked` in the ledger and maps to zero of the
  50 requirements. Research discusses it at length; that is background, not scope. Un-parking
  DW-106 alone would be the highest severity-to-effort addition available — that is a human's
  call, not this roadmap's.
- **Three human gates set the schedule's real risk**, not any implementation: the `GlobalHotkey`
  accessor and the packaging format (both in Phase 1), and the `CorrectionFailureKind` question
  (Phase 2, Wave E). Each is named in its phase's success criteria so it surfaces at planning time.
- **No new test, gate or CI work is scheduled.** Removed from scope 2026-08-31. Existing tests
  still run and must not be broken, but no phase adds a gate, fixes a flake, or makes a runtime
  observation. Closure evidence for every phase is inspection of the code.

### Phase 1: Hotkey Truth

**Goal:** A binding the daemon reports is the binding the display server actually holds, and a backend that is missing or refuses degrades visibly instead of lying or preventing startup
**Mode:** mvp

**Requirements:** HOTKEY-01, HOTKEY-02, HOTKEY-03, HOTKEY-04, HOTKEY-06, HOTKEY-07, HOTKEY-08, HOTKEY-09, HOTKEY-10, ARCH-02
**Success Criteria** (what must be TRUE):

1. **Two human decisions are recorded before any implementation task in this phase is planned.** (a) Whether `GlobalHotkey` gains a synchronous current-registration accessor beside `bindingChanges` — this edits AD-9's verbatim-frozen declaration; research recommends doing it, ratification is the human's. (HOTKEY-03, HOTKEY-04)
4. A consumer can tell "no backend" from "this key refused" from "binding revoked" without parsing a message string. (HOTKEY-08)
5. The remaining ambiguities on this surface are settled: the precedence between `bind()`'s returned outcome and the `bindingChanges` stream is stated, `HotkeyBinding.modifiers` cannot be mutated behind its `const` constructor, and the `libkeybinder` hardness re-measure trigger names a version the tree can observe changing. (HOTKEY-07, HOTKEY-09, HOTKEY-10)
