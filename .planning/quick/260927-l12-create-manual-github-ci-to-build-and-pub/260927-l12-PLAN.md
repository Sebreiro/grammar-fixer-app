## Task 3: Publish only verified packages from a manual GitHub workflow

**action:** Make `tool/release_version.dart` a pure, testable version planner over pubspec core, bump input, original branch ref, and fetched remote tag names. Accept only `refs/heads/` dispatches and `major|minor|patch`; parse `1.0.0+1` as core `1.0.0` and ignore legacy `v1.0` when matching stable three-part tags. On `main`, choose the bumped `X.Y.Z`, write `version: X.Y.Z` only in the runner checkout, and return `vX.Y.Z`. On other branches, derive the bump from current `origin/main` pubspec, normalize a readable lowercase ASCII branch slug, add a short deterministic digest when normalization/truncation loses identity, choose `max(existing N)+1` for `vX.Y.Z-slug.N`, and use `X.Y.Z~slug.N` in Debian metadata. Reject empty slugs, malformed versions, ambiguous/foreign tags, and duplicate release names. Keep the temporary prerelease pubspec change uncommitted. Add a separate `retry_tag` planner mode that parses the exact stable/prerelease tag version rather than consulting the bump or selecting another sequence. Test major/minor/patch, the initial `1.0.0+1`/`v1.0` case, branch slashes/case/unicode/collision cases, existing sequence tags, stable/prerelease failure cases, and recovery of an existing version without increment.

Create `.github/workflows/release.yml` with only `workflow_dispatch`, a required choice input `major|minor|patch`, and an optional `retry_tag` input. A nonempty `retry_tag` selects recovery mode and ignores the bump; it must never run the new-version path. Use a single workflow-wide `linux-release` concurrency group with `queue: max` and `cancel-in-progress: false`; scope `contents: write` to the publishing job. Check out the dispatched SHA with full history, fetch `origin/main` and remote tags, use Flutter 3.44.8 and explicit Linux/Flatpak/AppImage build dependencies from trusted, version/checksum-pinned sources, then run `flutter pub get`, `dart analyze --fatal-infos`, `tool/provision_sidecar.sh`, the same headless `flutter test --coverage --branch-coverage --exclude-tags=live test` and `dart run tool/check_coverage.dart coverage/lcov.info` checks as the current CI workflow, and Tasks 1-2's package/verifier commands. Ensure none of the four packages can be skipped or published if any check fails. On a new `main` release, confirm the dispatch SHA still equals `origin/main` before building and again before push. After successful verification, commit only `pubspec.yaml`, create an annotated tag recording a fixed workflow marker, source ref, source SHA, version, and target SHA, then `git push --atomic origin HEAD:refs/heads/main refs/tags/vX.Y.Z`; a non-fast-forward, ruleset rejection, duplicate tag, or unsupported atomic push is a hard failure, never a force push or automatic rebase of built assets. On a new branch release, annotate the tag with the same provenance fields, target the selected source SHA, and push only that new tag; on tag collision re-fetch, choose the next sequence, rebuild/reverify versioned assets, then retry without overwriting a remote tag.

For `retry_tag`, require the remote annotated tag to exist and contain the workflow marker plus exact selected source ref, source SHA, target SHA, and version. Check its target commit equals the recorded target and that the tag belongs to the dispatched branch: stable target must contain the tagged `pubspec.yaml` version and be on `main`; prerelease target must equal the recorded source SHA and be reachable from its source branch. Reject a lightweight, malformed, mismatched, or foreign tag and a conflicting published release. Check out the verified tag target, set the same temporary prerelease pubspec version if needed, rebuild all four assets, and re-run every test and package check. Recovery must bypass the original dispatch-SHA-equals-current-`main` guard because the stable push intentionally moved `main`; it must perform no commit, tag creation, or ref push. If a matching draft release exists, compare each existing asset's name, size, and SHA-256 digest against the local verified file, upload only missing assets, and fail on any mismatch instead of using `--clobber`. If no release exists, create a draft using `gh release create --verify-tag`; verify the four uploaded assets and publish only once the exact set matches. A complete published release is an idempotent success only when all four remote assets match; otherwise fail for operator review. Set `--prerelease --latest=false` for branch runs. Never let `gh` synthesize a missing tag. Document normal and recovery dispatch examples, artifact installation, local build and verification commands, Python runtime requirements, branch protection/token requirements, and that a real Wayland compositor check still requires a desktop host. Do not edit the existing merge-gate workflow.
